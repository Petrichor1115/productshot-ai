## 1. 目标

补齐作业要求中"管理员可以开账号"的能力：用户列表、创建用户、启用/禁用、角色调整，并纳入管理端导航。

## 2. 背景与范围

**问题**：v1.0 管理端只有内置 `admin`，无法开账号，也未实现用户禁用。这是作业要求的明确条目，属功能缺口而非优化项。

**在范围内**
- `GET / POST / PATCH /api/admin/users`
- 用户列表：用户名 / 角色 / 状态 / 注册时间 / 会话数 / 生图数
- 创建用户（指定初始角色）、禁用/启用、调整角色
- 管理端新增"用户管理"菜单项（插入在"用户反馈"之前）
- 删除保护：不能删除或禁用自己

**明确排除**
- 用户自助修改资料（昵称/头像）→ v1.2
- 批量导入 / 导出用户 → 悬空
- 用户分组与权限细分 → 超出双角色模型

## 3. 前置依赖

- T02（角色体系）、T09（管理端框架与 admin 守卫）

## 4. 任务清单

- [ ] users 表加 `status` 字段（active / disabled），默认 active
- [ ] `GET /api/admin/users`：分页 + 聚合会话数与生图数
- [ ] `POST /api/admin/users`：创建用户，用户名唯一校验，默认角色 user
- [ ] `PATCH /api/admin/users/:id`：改角色 / 改状态
- [ ] 禁用用户立即失效：校验 `status` 于 auth 中间件
- [ ] 自我保护：不能禁用/降级当前登录管理员
- [ ] 管理端新增"用户管理"菜单 + 列表视图 + 操作按钮
- [ ] 所有操作二次确认，错误提示可读

## 5. 关键实现

```js
// auth 中间件增加状态校验，禁用即时生效
const user = getUserById(payload.id);
if (user.status !== 'active') return res.status(403).json({ error: '账号已被禁用' });

// 自我保护
if (Number(id) === req.user.id) return res.status(400).json({ error: '不能操作当前登录账号' });
```

**即时失效**：禁用后该用户已签发但未过期的 token 需在下次请求被拦，故在 auth 中间件查库校验 `status`，而非只信 token 内容。

## 7. 验收标准（AC）

1. 管理员可创建新用户，新用户能立即登录。
2. 重名创建被拒并提示。
3. 禁用用户后，其已登录会话在下次请求被 403 拦截。
4. 重新启用后恢复正常访问。
5. 管理员无法禁用或降级自己，操作被拒且有提示。
6. 用户列表的会话数与生图数与生图记录页一致。
7. 非管理员调用所有 `/api/admin/users*` 返回 403。

## 9. 风险与决策

| 决策 | 原因 |
|------|------|
| 禁用不改密码、不删数据 | 保留可追溯性，启用即恢复 |
| auth 中间件查库校验 status | 保证禁用即时生效，代价是每次请求多一次查询 |
| 菜单插在"用户反馈"前 | 保持 PRD 原有四菜单相对顺序不变 |
