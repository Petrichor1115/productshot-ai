# T27 · 用户通知与消息中心

> 状态：⬜ Todo ｜ 优先级：P2 ｜ 阶段：v1.2 运营与体验
> 依赖：T18、T21、T19 ｜ 来源：T18 遗留项（用户端进度展示与通知）· T12 遗留项（异地登录提醒）
> 规格状态：v1.2 规划；PRD v2.1 未定义通知机制

## 1. 目标

建立站内通知体系：任务完成、反馈被处理、额度不足、异常登录等事件主动触达用户，并在用户端提供统一的消息中心与已读管理。

## 2. 背景与范围

**问题**：v1.0 用户只能靠停留在页面等待才能知道结果；反馈处理进度用户不可见（T18 决策产品端暂不展示）；安全事件无任何提醒。信息全部单向沉淀在管理端。

**在范围内**
- `notifications` 表：用户 / 类型 / 标题 / 内容 / 关联对象 / 已读态 / 创建时间
- 事件源：任务完成或失败（T21）、反馈状态变更（T18）、额度不足（T19）、异常登录（T12）
- 用户端消息中心：铃铛入口 + 未读数 + 列表 + 已读 + 跳转
- 未读数轮询与已读态同步

**明确排除**
- 邮件 / 短信 / App 推送 → 无服务端通道，悬空
- WebSocket 实时推送 → 轮询已足够，避免过度设计
- 用户自定义通知偏好（订阅哪类）→ v1.3
- 系统公告与运营推送 → v1.3

## 5. 关键实现

```js
// 统一入口：所有事件都走这里，便于去重与扩展
function notify(userId, type, { title, content, link }) {
  const dup = dbGet(
    'SELECT id FROM notifications WHERE user_id=? AND type=? AND link=? AND created_at > ?',
    [userId, type, link, minutesAgo(5)]
  );
  if (dup) return;                 // 5 分钟内同事件去重
  db.run('INSERT INTO notifications (...) VALUES (...)', [...]);
}
```

**去重必要性**：任务重试、轮询补偿等场景容易重复触发事件，不去重会让消息中心被同一条消息刷满，反而失去提醒价值。

## 7. 验收标准（AC）

1. 任务完成后 10 秒内消息中心出现对应通知，点击可跳到结果。
2. 任务失败通知包含可读的失败原因。
3. 管理员处理反馈后，提交者收到通知。
4. 额度低于阈值时收到提醒且提醒不重复刷屏。
5. 未读数与实际未读条数一致，标记已读后红点消失。
6. 通知严格按用户隔离，越权不可见。
7. 同一事件 5 分钟内只产生一条通知。

## 9. 风险与决策

| 决策 | 原因 |
|------|------|
| 轮询而非 WebSocket | 通知非强实时；轮询实现与运维成本低得多 |
| 站内通知而非邮件短信 | 无第三方通道；站内已能覆盖主要场景 |
| 事件去重窗口 5 分钟 | 兼顾重试补偿与真实重复操作 |
