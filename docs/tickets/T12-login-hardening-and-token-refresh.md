# T12 · 登录安全加固与令牌刷新

> 状态：⬜ Todo ｜ 优先级：P1 ｜ 阶段：v1.1 安全
> 依赖：T02 ｜ 来源：T02 遗留项
> 规格状态：v1.1 规划，PRD v2.1 未覆盖

## 1. 目标

补齐认证环节的安全缺口：登录失败限流、令牌刷新机制、密码找回与修改，降低暴力破解与长期令牌泄露风险。

## 2. 背景与范围

**问题**：T02 的 JWT 有效期 7 天且无法刷新，一旦泄露影响周期长；登录接口无失败次数限制，可被暴力枚举。

**在范围内**
- 登录失败限流（按用户名 + IP 双维度）
- Refresh Token 机制，Access Token 缩短至 2 小时
- 修改密码（需校验原密码）
- 登出时令牌失效（黑名单或版本号）

**明确排除**
- 短信 / 邮箱验证码找回密码（无第三方服务）→ 悬空
- 双因素认证（2FA）→ v1.2
- 图形验证码 → 视限流效果再定

## 3. 前置依赖

- T02（认证与 JWT）

## 4. 任务清单

- [ ] 登录失败计数：同用户名连续 5 次失败锁定 10 分钟
- [ ] 同 IP 维度限流，防止跨用户名撞库
- [ ] Access Token 缩至 2h，签发 Refresh Token（7d）
- [ ] 新增 `POST /api/auth/refresh`
- [ ] 新增 `POST /api/auth/change-password`
- [ ] 用户表加 `token_version` 字段，改密/登出时自增使旧令牌失效
- [ ] 前端 `api.js` 接入 401 自动刷新重试
- [ ] 失败提示保持"用户名或密码错误"不变，另提示剩余尝试次数

## 5. 关键实现

```js
// 令牌版本号：改密 / 登出即自增，旧 Access Token 自然失效
UPDATE users SET token_version = token_version + 1 WHERE id = ?;

// jwt 校验时比对版本
const payload = jwt.verify(token, SECRET);
if (payload.tv !== user.token_version) return res.status(401).json({ error: '令牌已失效' });
```

**限流存储**：v1.1 用进程内 Map（单机足够）；多实例部署时需换 Redis。

## 7. 验收标准（AC）

1. 连续 5 次密码错误后，第 6 次被拒并提示锁定剩余时间。
2. 锁定期间即使密码正确也无法登录；10 分钟后自动恢复。
3. Access Token 过期后，前端静默刷新并重试原请求，用户无感。
4. 修改密码后，原设备的 Access Token 立即失效需重新登录。
5. 登出后该令牌不可再用于任何接口。

## 9. 风险与决策

| 决策 | 原因 |
|------|------|
| 进程内 Map 存限流 | 单机演示足够；已记录多实例需换 Redis |
| 用 token_version 而非黑名单 | 无需额外存储，O(1) 校验 |
| 不做图形验证码 | 限流已能挡住绝大部分撞库，避免过度影响体验 |
