# T26 · 套餐订购与支付对接

> 状态：⬜ Todo ｜ 优先级：P2 ｜ 阶段：v1.2 商业化
> 依赖：T19、T13 ｜ 来源：T19 遗留项（真实支付、套餐与订单）
> 规格状态：v1.2 规划；PRD v2.1 未定义套餐与订单模型
> ⚠️ 阻塞项：真实支付通道需商户资质，当前不具备，本期只做**订单与套餐闭环 + 模拟支付**

## 1. 目标

建立套餐、订单与支付回调的完整闭环：用户可选套餐下单、支付成功后自动加额度、订单可查询可对账，为未来接入真实支付通道留好接口。

## 2. 背景与范围

**问题**：T19 只做了额度计量与赠送，没有"用户自己能买"的路径，商业化闭环缺一环。

**在范围内**
- `plans` 套餐表（名称 / 额度 / 价格 / 有效期 / 上下架）
- `orders` 订单表（订单号 / 用户 / 套餐 / 金额 / 状态 / 支付时间）
- 下单 → 支付 → 回调加额度 → 订单置为已支付
- 支付回调幂等（重复回调只加一次）
- 管理端：套餐上下架、订单列表与对账
- 支付通道抽象为接口，默认实现为"模拟支付"

**明确排除**
- 真实微信 / 支付宝支付 → **无商户资质，阻塞**，接口预留
- 退款、发票、优惠券 → v1.3
- 订阅制自动续费 → v1.3
- 按 `gen_type` 差异化套餐 → 待 T17/T22 的用量数据积累后再定

## 5. 关键实现

```js
// 幂等加额度：以订单状态为条件，重复回调不会二次加额度
const changed = db.run(
  "UPDATE orders SET status='paid', paid_at=? WHERE order_no=? AND status='unpaid'",
  [now, orderNo]
).changes;
if (changed === 0) return res.json({ success: true, data: { duplicated: true } });
addCredits(userId, plan.credits, 'purchase', orderNo);
```

**价格快照**：订单表冗余下单时的价格与额度，套餐后续调价不影响已成交订单，这是能对账的前提。

## 7. 验收标准（AC）

1. 下单生成唯一订单号，状态为 `unpaid`，此时额度不变。
2. 支付回调成功后额度立即增加，订单状态变为 `paid`。
3. 同一订单重复回调 3 次，额度只加一次，且回调返回成功。
4. 套餐下架后不再出现在用户端，但历史订单不受影响。
5. 订单金额与额度流水可对账（订单合计 = 赠送流水合计）。
6. 未登录不能下单；越权查询他人订单返回 404。
7. 支付失败回调不改变订单状态与额度。

## 9. 风险与决策

| 风险 | 应对 |
|------|------|
| **无商户资质，真实支付不可做** | 本期用 mock 通道跑通闭环；`pay()` 接口预留，有资质后替换实现即可 |
| 回调伪造 | 必须验签；mock 阶段用共享密钥 + 时间戳窗口，不得裸奔 |
| 加额度与订单状态不一致 | 先更新订单状态再发额度，以 `changes` 判定是否真正成交 |
