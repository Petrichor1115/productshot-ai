# T28 · 会话管理与检索增强

> 状态：⬜ Todo ｜ 优先级：P2 ｜ 阶段：v1.2 用户端
> 依赖：T07、T04、T14 ｜ 来源：T07 遗留项（会话重命名 / 搜索 / 置顶）· T14 遗留项（消息全文检索）
> 规格状态：v1.2 规划；PRD v2.1 §3.2.3 仅定义列表的增删改查

## 1. 目标

让会话从"只能新建和删除"升级为可管理、可检索的资产：支持重命名、置顶、归档，并能按会话名、补充信息与对话内容全文检索。

## 2. 背景与范围

**问题**：会话积累后侧边栏变成一长串无意义时间戳，找不到也认不出。T14 存了消息流水但没提供检索入口，数据存了却用不上。

**在范围内**
- 重命名、置顶、归档（归档后默认隐藏，可切换查看）
- 检索：会话名 + 补充信息 + 消息内容（T14）
- 排序：置顶优先，其余按最近活动
- 管理端会话记录同样支持按用户名 / 会话名检索

**明确排除**
- 标签体系与自定义分组 → v1.3
- 批量操作（批量删除 / 归档）→ v1.3
- 智能分组与自动命名 → 需 LLM 介入，悬空
- 跨用户内容检索（管理员搜用户对话内容）→ 合规敏感，悬空

## 5. 关键实现

```sql
-- 检索：会话名 / 补充信息 / 消息内容三路命中取并集
SELECT DISTINCT s.* FROM sessions s
LEFT JOIN messages m ON m.session_id = s.id
WHERE s.user_id = ?
  AND (s.name LIKE ? OR s.supplement LIKE ? OR m.content LIKE ?)
ORDER BY s.is_pinned DESC, s.updated_at DESC;
```

**FTS5 评估结论**：会话与消息量在万级以下时，LIKE 已足够且零依赖；若消息表达到十万级再引入 SQLite FTS5 虚拟表，届时只需替换查询实现。

## 7. 验收标准（AC）

1. 重命名后列表即时更新，刷新后仍保持。
2. 置顶会话固定在列表顶部，取消后置顶失效。
3. 归档会话默认不显示，切换"查看归档"后可见。
4. 搜索关键词能命中会话名、补充信息与对话内容三类。
5. 搜索结果只返回当前用户的会话，无越权泄露。
6. 无匹配时显示空态而非报错。
7. 管理端按用户名或会话名检索结果正确。

## 9. 风险与决策

| 风险 | 应对 |
|------|------|
| LIKE 全表扫描变慢 | 先实测；超阈值再上 FTS5，接口层保持不变 |
| 搜索命中消息片段缺少上下文 | 结果展示命中片段的前后文各 20 字 |
| 归档语义与删除混淆 | 归档可恢复，删除不可恢复，UI 文案明确区分 |
