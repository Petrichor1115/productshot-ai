# T19 · 用量计费与易点余额

> 状态：⬜ Todo ｜ 优先级：P2 ｜ 阶段：v1.1 商业化
> 依赖：T06、T07 ｜ 来源：T07 遗留项（易点余额为静态数字）· T06 遗留项（无配额）
> 规格状态：v1.1 规划，PRD v2.1 未定义计费模型

## 1. 目标

把静态的"易点余额"变为真实可用的计量体系：按生成张数扣减、额度不足拦截、套餐与赠送，并在管理端可查看用量。

## 2. 背景与范围

**问题**：v1.0 侧边栏"剩余 20 易点"是写死数字，生成不扣减也无上限，无法支撑真实运营。

**在范围内**
- 用户额度字段与流水表
- 生成前校验余额、生成成功后扣减（按实际成功张数）
- 额度不足时拦截并提示，不产生半成品数据
- 管理端可查看各用户用量与余额
- 赠送额度（管理员手动）

**明确排除**
- 真实支付（微信 / 支付宝）→ 无商户资质，悬空
- 套餐订购页与订单 → v1.2
- 不同模型差异化定价 → 待 T17 稳定后再定（已预留 `gen_type`）

## 3. 前置依赖

- T06（生成服务与成功张数）、T07（余额展示位）

## 4. 任务清单

- [ ] users 表加 `credits` 字段（默认赠送额度）
- [ ] 建 `credit_logs` 流水表：用户 / 变动量 / 类型 / 关联记录 / 余额快照
- [ ] 生成前校验：`credits >= 将生成的张数`
- [ ] 生成后按**实际成功张数**扣减（失败不扣）
- [ ] 扣减与写流水在同一事务内，避免重复扣
- [ ] 前端余额实时刷新，不足时禁用生成并提示充值
- [ ] 管理端用户管理（T13）中展示余额并支持赠送
- [ ] 并发生成的余额竞争处理

## 5. 关键实现

```js
// 失败不扣费：只统计实际成功张数
const successCount = results.filter(r => r.status === 'success').length;
if (successCount > 0) {
  db.run('UPDATE users SET credits = credits - ? WHERE id = ? AND credits >= ?',
         [successCount, userId, successCount]);
  insertLog({ userId, delta: -successCount, type: 'consume', balanceAfter });
}
```

**并发安全**：`UPDATE ... WHERE credits >= ?` 利用 SQL 条件原子性，避免并发下扣成负数；受影响行数为 0 时判定额度不足。

## 7. 验收标准（AC）

1. 生成成功 3 张扣 3 点，失败的那张不扣。
2. 余额不足时点击生成被拦截，不产生 generations 记录。
3. 流水表余额快照连续可核对，无跳变。
4. 并发发起两次生成不会扣成负数。
5. 管理员赠送额度后用户侧立即生效。
6. 余额与流水可对账（初值 - 消耗 + 赠送 = 当前值）。

## 9. 风险与决策

| 决策 | 原因 |
|------|------|
| 失败不扣费 | 用户体验优先；若被滥用再改为"发起即扣" |
| 不做真实支付 | 无商户资质；以"赠送额度"跑通计量闭环 |
| 扣减用 SQL 条件而非先查后写 | 避免并发下超扣 |
