## 1. 目标

把项目从"本地能跑"推进到"可部署、可监控、可回归"：容器化与进程守护、数据备份与恢复、健康检查与关键指标、核心逻辑单元测试与 CI 回归。

## 2. 背景与范围

**问题**：T20 补齐了日志与冒烟，但仍有四个缺口：部署靠手动 `node server.js`、数据库无备份、线上健康状态不可知、核心逻辑（计费、权限）无单测保护。这些在 v1.2 功能变多后会直接变成事故源。

**在范围内**
- Dockerfile 与 `docker-compose.yml`，数据卷挂载 `data.db` 与 `uploads/`
- 进程守护与优雅退出（确保退出前 flush 数据库）
- `data.db` 定时备份与恢复演练
- `/api/health` 健康检查（含数据库与磁盘可写性）
- 关键指标：请求量、错误率、出图耗时 P50/P95、方舟调用量
- 单元测试：计费扣减、权限校验、JSON 字段容错
- CI：lint + 单测 + 冒烟（T20 的 smoke 脚本）

**明确排除**
- K8s / 多可用区 / 自动扩缩容 → 规模未到
- 第三方 APM 平台接入 → 需账号与费用，先自建指标端点
- 全量单测覆盖 → 只覆盖高风险核心逻辑
- 第三方内容审核服务 → 无密钥预算，T20 已预留接口

## 3. 前置依赖

## 5. 关键实现

```js
// 优雅退出：顺序很重要，先停新任务、再落盘、最后退出
process.on('SIGTERM', async () => {
  server.close();          // 停止接收新请求
  await drainQueue();      // 等待在途任务收尾（T21）
  persist();               // 强制落盘，避免丢数据
  process.exit(0);
});
```

```yaml
# docker-compose 关键：数据与上传目录必须挂卷，否则容器重建即丢
volumes:
  - ./data:/app/data
  - ./uploads:/app/uploads
```

**单测优先级**：计费与权限是"错了会直接造成资金与数据泄露"的逻辑，必须测；渲染与 CRUD 靠冒烟覆盖即可，避免为覆盖率而写无意义断言。

## 7. 验收标准（AC）

1. `docker compose up` 能一次启动，服务可访问且数据卷正确挂载。
2. 容器重建后用户数据与上传图片不丢失。
3. `docker compose down` 时数据库已正确落盘，重启后数据完整。
4. `/api/health` 在数据库异常或磁盘不可写时返回非健康状态。
5. 备份脚本可生成备份文件，且用备份还原后数据条数一致。
6. 单测覆盖计费并发、失败不扣费、越权三类，全部通过。
7. CI 在单测失败时中止，不进入冒烟。
8. 部署文档能让第三人照做完成一次完整部署。

## 9. 风险与决策

| 风险 | 应对 |
|------|------|
| sql.js 全量导出在数据量变大后拖慢退出 | 退出前强制 flush，接受短暂延迟；量大则考虑迁移原生 SQLite（重大决策，需单独评估） |
| 容器内时间与本地时区不一致影响统计口径 | 镜像显式设置 `TZ=Asia/Shanghai`，与 `datetime('now','localtime')` 保持一致 |
| 单测引入测试框架增加依赖 | 优先用 Node 内置 `node:test`，零额外依赖 |
